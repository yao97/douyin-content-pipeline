# 04 · 文案转写

把 `.m4a` 变成**结构化逐字稿知识库**（md + 关键词 + 内容总结 + 封面）。
这是整条流水线价值最高、也是最耗时的环节（端到端 RTF ≈ 0.85，即 1 小时音频约需 51 分钟）。

主体程序在另一个工作区 `D:\视频\媒体知识库`，本仓库只收录**接口层与渲染守护**，以及完整的调用约定。

---

## 1. 组件与角色

| 组件 | 位置 | 作用 |
|---|---|---|
| ASR 引擎服务 | `video-analyzer/backend/transcribe_server.py`，`127.0.0.1:8766` | 收音频、跑 ASR、吐转写结果 |
| `asr_batch.py` | 媒体知识库 | 批处理编排：`stage1`（转写）/ `stage2`（渲染）/ `registry` / `accept` / `retry` / `slice` |
| `_stage2_daemon.py` | 媒体知识库 | 渲染守护：轮询新 raw → 生成 md + 复制封面 |
| `lib_source.py` | 媒体知识库 | **适配层**：扫描 `自媒体视频库`，产出任务列表 |
| `webui.py` | 媒体知识库，`127.0.0.1:8770` | 实时看板（进度 / 流式逐词 / 下载进度） |
| `checkpoint.py` | 媒体知识库 | 诊断 + 尽力拉起（尾行打 `ACTION:`） |
| `_asr_registry.json` | 媒体知识库 | **增量重跑的唯一依据** |

> ⚠️ ASR 服务由 **Windows 服务 `VideoAnalyzer-Transcribe`（nssm 托管）** 守护，
> 5 秒自动重启。**绝不要自己 `Popen` 拉起** —— 会产生抢不到端口的僵尸实例。
> 需要重启时走 `Restart-Service VideoAnalyzer-Transcribe`。

## 2. 数据源适配（`lib_source.py`）

转写侧通过 `WB_SOURCE` 开关选择数据源：

| 值 | 数据源 |
|---|---|
| `lib` | **本流水线使用**：`D:\视频\自媒体视频库`（`.m4a` + 同目录封面 + `Data/UID*.csv`） |
| `guanzhu`（默认） | 旧源 `C:\Users\EDY\Videos\data\关注` |

```bash
set WB_SOURCE=lib
python asr_batch.py stage1
```

`build_lib_tasks()` 的核心逻辑：

1. 扫描 `UID*_发布作品` **和** `MID*_合集作品` 两类目录（合集目录曾被漏掉）。
2. 音频优先 `.m4a`；没有 m4a 时才用**已稳定**（mtime > `WB_LIB_FRESH_SEC`=120s）的 `.mp4` 兜底。
3. 作品 ID 提取：
   - 文件名里有 15 位以上数字 → 直接用；
   - **合集文件名没有 ID** → 用 `发布时间`（`YYYY-MM-DD HH.MM.SS` 前缀）去 CSV 对号入座。
4. 元数据（作者 / 标题 / 发布时间 / 时长）从 `Data/<目录名>.csv` 取，**CSV 优先于文件名**。
5. 封面 = 同目录、同 stem、不同扩展名（`.jpeg/.jpg/.png/.webp`）。

> ⚠️ **任务字典的时长字段是 `dur_csv`（秒，字符串），不是 `duration`**。
> 用错字段会静默得到 0，导致「剩余音频 0.00h」这类假结论。

合集 CSV 里的「账号昵称」是**合集名**而不是作者名：

## 3. ASR 服务接口（:8766）

| 接口 | 说明 |
|---|---|
| `GET /` | 健康检查（返回 200 即存活） |
| `GET /api/status/<job_id>` | **实时真相**：`progress` / `current_chunk` / `elapsed_sec` / `detail` |
| `GET /api/history/transcribe?limit=N` | 作业历史（⚠️ SQLite 过期快照，别当实时用） |
| `POST /api/transcribe-start` | 指定 `{job_id, engine}` 启动/救活作业 |

### 3.1 `progress` 状态码

| 值 | 含义 |
|---|---|
| `2` | 排队中 |
| `15` | 转写中（`current_chunk` 有内容并持续变长 = 真的在跑） |
| `20` | 音频就绪（**长期不动 = 服务崩溃遗留的僵尸作业**） |
| `100` | 完成 |

### 3.2 判「卡住」vs「真在跑」

```
① 取 /api/history/transcribe?limit=5 里最新一条 job_id
② 查 /api/status/<job>：status=transcribing 且 current_chunk 在变长 → 真的在跑
   （隔 60~90 秒看两次，比只看一眼靠谱）
③ 最快确诊僵尸：查 8766 进程启动时间 ——
   启动时间晚于作业提交时间 = 服务崩过，该作业必是僵尸
```

**僵尸作业处置**：`progress=20` 意味着「结果没被取走」，不是白跑。
wav 通常还在 `C:\Windows\Temp\video_analyzer\<job>.wav`（服务以 SYSTEM 跑，这是服务端真实 TEMP），
可直接救活（零损耗）：

```bash
curl -s -X POST http://127.0.0.1:8766/api/transcribe-start \
  -H "Content-Type: application/json" \
  -d '{"job_id":"<job>","engine":"qwen3_asr"}'
```

### 3.3 崩溃是常态，不是例外

- 崩溃真身：`llama.cpp` 的 C++ 断言
  `GGML_ASSERT(i01 >= 0 && i01 < ne01) failed` → `abort()`，所以 Python 侧「零 traceback」。
- 取证只看三处：`video-analyzer/backend/logs/service.err.log`（nssm 的 AppStderr，**真正的现场**）、
  `Get-WinEvent Application`（`Application Error ID=1000`）、`Get-WinEvent System`（nssm 重启记录）。
  工作区里的 `_asr_server.log` **在 nssm 托管时根本不更新**，拿它判「服务端有没有输出」必然误判成卡死。
- 崩溃间隔实测 9~18 分钟一次，而单个切片段转写耗时 7~7.5 分钟 —— **两者同量级**。
- 已在客户端做「基础设施故障分流」：拒连/超时/5xx 走 `SLICE_INFRA`(6) 预算、**不吃** `SLICE_RETRY`(3) 名额，
  退避后重提。日志里的「基础设施故障 i/6（不计入 3 次尝试）」是**正常自愈**。

## 4. 长视频：切段转写再拼接

**规则：时长 ≥ 20 分钟（`WB_SLICE_MIN`=1200s）即自动切片。**

```
段数  = ceil(dur / 900)          # 15 分钟一段，必须向上取整
段长  = ceil(dur / 段数)          # 必须按浮点算，否则会低估覆盖
```

> ⚠️ **必须向上取整**，向下取整会留碎屑尾段（如 16685s 多出 3s 段 → 白跑一次 ASR）。
> ⚠️ **必须按浮点算**：旧的 `-(-int(dur)//SEC)` 会截断小数（900.1s 只切 1 段 900s，覆盖不足）。

### 4.1 为什么必须切

把一条 5 小时音频整条丢给 8766，一旦中途崩溃就整条白跑（45 分钟 ~ 3 小时）。
切片后每段独立落盘 → 崩了只重跑未完成的段。

### 4.2 段缓存与断点续跑

- 缓存目录 `_slice_tmp/<vid>/`，逐段转写、逐段落盘 `seg_%03d.json`。
- **幂等键是文件名，不是段时长** → 改段长要 `force=True` 或先删 `_slice_tmp/<vid>`。
- 全段完成后合并成标准 raw + `mark_ok` → 下游 stage2 零改动。
- **孤儿段可捞回**：客户端被杀时，服务端某段 job 已 `done` 但 json 没落盘 →
  下次用 `find_done_job_by_name(_slice_upload_name(vid, tag, k))` 认领复用。
  判据：**段 k（1 基）↔ `seg_%03d.json`（k-1）↔ 上传名 `{vid}_{tag}_{k:03d}.mp4`**。

### 4.3 多源作品必须走切片

下载器会把超长作品切成多份（`_1/_2/_3`），vid 相同。
若只取第一个源，会**只转第一片、丢掉后面全部内容**。
现在 `len(srcs) > 1` 一律强制切片，`dur_est = sum(各源时长)`。

### 4.4 手工补跑

```bash
python asr_batch.py slice <vid>           # 单条
python asr_batch.py slice-all [门槛秒数]   # 批量未完成的长视频
```

> ⚠️ `slice` 子命令**不取 `_stage1.lock`** —— stage1 在跑时手工 slice 同一条作品会
> **重复提交 ASR 作业**（服务端单 worker 串行，同一段耗时翻倍，且**服务端没有 cancel 接口**，
> 只能白跑）。要手工补跑，先确认 stage1 已收工。

## 5. 转写注册表（`_asr_registry.json`）

增量重跑的**唯一依据**。

```jsonc
{
  "<vid>": {
    "ok": true,            // 是否已完成
    "author": "...", "pub": "2026-05-11",
    "duration": 1234.5,
    "chars": 80897,        // 逐字稿字数
    "job_id": "...", "ts": "...",
    "attempts": 0, "retry_rounds": 0,
    "abandoned": false,
    "note": ""
  }
}
```

### 5.1 判「已完成」要校验内容完整性

不能只看 `_asr_raw/<vid>.json` 存在，必须同时满足：

- `text` 非空且不是占位符；
- `duration > 0`；
- 字数 ≥ `WB_MIN_CHARS`（10）。

### 5.2 失败分类

| 情况 | 处理 |
|---|---|
| 重试达上限 `WB_MAX_ATTEMPTS`(2) | 标 `abandoned`（**不是死刑**，基础设施类可 `retry` 放行） |
| 源文件损坏（`corrupt_src`） | 标 `retry_rounds=3` 停手，**只能重下** |
| 几乎无语音 | `accept <vid> "备注"` 标 `low_content` |
| 基础设施故障 | 走 `SLICE_INFRA` 预算，**不吃**重试名额，退避等 8766 回来 |

### 5.3 ⚠️ 并发写入铁律

- **读**走 `_reg()`（按 `(mtime_ns, size)` 指纹自动重载，**不要永久缓存**）。
- **写**一律 `update_entry(vid, patch, remove, delete)`。
- **禁止整表回写**（`reg = _reg(); reg[vid] = …; save_registry(reg)`）——
  长跑进程会**静默抹掉别人的改动**。典型症状：`accept` 不生效、条目被重转、
  `retry` 放行后仍显示 `abandoned`。

### 5.4 ⚠️ `load_registry()` 读失败会抛错，这是有意设计

旧实现读失败静默返回 `{}`，等于「所有作品都没转过」→ 跑批会把 650+ 条全部重转
（上百小时、不可逆）。现在会：**重试一次 → 备份成 `_asr_registry.json.corrupt` → 抛 `RuntimeError`**。

> 看到「注册表读取失败」时**不要**去改脚本让它继续，而应人工检查注册表本身
> （`.corrupt` 就是现场备份）。

## 6. 渲染：raw → md（stage2）

`_stage2_daemon.py` 是一个轮询守护：

```python
while True:
    # 1) 扫 _asr_raw/*.json，找出「需要渲染」的条目
    #    md 不存在            → 全量生成
    #    md 存在但缺「## 视频内容总结」 → 复用原关键词，只补总结后重写
    #    md 已含总结          → 跳过
    # 2) 对每条：extract_keywords → extract_summary → render_md → 复制封面 → 写文件
    # 3) 检测 stage1 是否结束（在本次启动后写入的日志里找「阶段1 完成」）
    #    结束且无待办 → 退出
```

要点：

- **单实例锁** `_stage2.lock`，重复拉起直接退出。
- 「阶段1 完成」必须从**本次启动之后的日志偏移**里找，否则历史日志里已有的那句话会让守护进程立刻误判收工退出。
- **改 `asr_batch.py` 后必须重启 stage2 才生效**（它 `import asr_batch`）。
- stage1 **只转写不渲染 md**；stage2 不在跑 → 出了 raw 也不会有 md。

### 6.1 LLM 摘要的硬性约束

- 总结**只能基于逐字稿真实内容**，**严禁按标题脑补**。
- 逐字稿 < 60 字不生成摘要（降级为「无总结」）。
- LLM 配置走 `_llm_config.sh`（**含明文密钥，不入版本库**）。

### 6.2 md 结构

```markdown
作者 / 抖音账号 / 作品ID(链接) / 视频标题 / 发布时间 / 关键词(4 个、顿号)
视频封面：![封面](<同 md 名>)
-----
## 视频内容总结
### 视频核心主旨
### 核心干货要点
### 内容整体逻辑
-----
## 逐字稿
<正文>
```

**逐字稿与封面同名、仅扩展名不同**，封面随源文件走（不能裸 `作品ID.jpg`）。

## 7. 看板（:8770）

本机 `http://127.0.0.1:8770/`，局域网 `http://192.168.0.8:8770/`。

| 接口 | 内容 |
|---|---|
| `GET /api/live` | 实时转写状态（当前条目 / 进度 / 流式文本） |
| `GET /api/download` | 视频下载进度（按账号 + 正在下载） |
| `POST /api/quit` | **重启看板的正确方式**（看板自己退出，0 风险） |

### 7.1 进度怎么算

服务端 `progress` 只有几档，形同没有。看板自己算：

```
进度 = elapsed / (dur × WB_RTF)
```

- `elapsed` 取 `/api/status/<job>.elapsed_sec`（**真实耗时**）；
- `WB_RTF` 默认 0.85（端到端有效 RTF，批量估时用它，不要用单条打印值）；
- **切片条目**改用「已完成段音频秒数 + 当前段已跑」/ 总音频秒数
  （服务端 `elapsed` 只覆盖当前段，按整条算会一直显示 ~5%，看起来像卡死）。

### 7.2 「当前条目」是**打分排序**，不是任务顺序

给每个未完成 vid 打分取最大：`(状态权重 transcribing=2 > waiting=1 > audio_ready=0, 活动时间戳)`，
时间戳须在 `LIVE_JOB_WIN` 内（audio_ready 300s / waiting 600s / transcribing 不过期）——
这就是**僵尸过滤器**。

**一眼校验**：`item.vid` 必须等于 `_slice_tmp/` 下**最新被写入**的目录名。

### 7.3 作业必须取「最新提交」的那个

服务端重启会留下 `audio_ready` 的僵尸 job（状态永不推进），
若「优先找活跃的」它就会盖住真正最新、已 `done` 的作业 →
看板显示「已跑 107:42 / 音频就绪 91.5% / 引擎无任何输出」这种彻头彻尾的假象。
修法：按 `created_at` 倒序取第 0 个。

> 症状识别：**elapsed 远超该段合理耗时（>30 分钟）+ 状态卡在「音频就绪」+ 引擎无输出**
> → 八成是僵尸 job，别急着判定「跑批卡死」。

### 7.4 `stream_src` 字段

| 值 | 含义 |
|---|---|
| `engine` | 引擎实时 token 流（**正常**） |
| `log` | 取不到 `current_chunk`，回退读工作区 `_asr_server.log` —— **nssm 托管时该文件不更新**，会显示几小时前的陈旧文本，极易误判成卡死 |

### 7.5 逐词流式输出的实现

引擎 `asr.py::_decode()` 默认 `streaming=True`，本就逐 token `print(..., end='')` 到 stdout。
`transcribe_server.py` 的 `_JobStreamTee` 在 `engine.asr()` 期间替换 `sys.stdout`，
把内容累积进 `jobs[job_id]["current_chunk"]`，而 `/api/status` 本来就会返回该字段。

**没有改第三方引擎代码。**

> ⚠️ `transcribe_qwen3_asr()` 里**不能**出现局部 `import sys` —— 会让 `sys` 变局部变量 → `UnboundLocalError`。

## 8. 相关配置变量速查

| 变量 | 默认 | 含义 |
|---|---|---|
| `WB_SOURCE` | `guanzhu` | **本流水线必须设为 `lib`** |

| `SLICE_INFRA` | `6` | 单段基础设施失败预算（**不吃**上面那个名额） |
