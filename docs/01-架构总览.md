# 01 · 架构总览

## 1. 两库分离

整条流水线横跨两个工作区，职责严格分离：

```
D:\视频\自媒体视频库            D:\视频\媒体知识库
┌────────────────────┐         ┌────────────────────┐
│  采集侧（可重建）    │         │  知识侧（只增不删）  │
│                    │  .m4a   │                    │
│  UID*_发布作品/     ├────────►│  <作者>/           │
│  MID*_合集作品/     │  封面    │    日期_作者_ID.md  │
│  Data/*.csv        │────────►│    日期_作者_ID.jpeg│
│  Volume/*.db       │         │  _asr_registry.json│
└────────────────────┘         └────────────────────┘
```

| | 采集侧 | 知识侧 |
|---|---|---|
| 内容 | 音视频原文件 + 元数据 CSV + 下载 DB | 逐字稿 md + 封面 + 转写注册表 |
| 可重建性 | **可以重建**（重下即可） | **不可重建**（转写成本高，是核心资产） |
| 允许的操作 | 删除、改名、重下、上传 | 只能新增；重写需谨慎 |
| 命名规范 | `日期_昵称_作品ID.ext` | 同左（与采集侧成品名一致） |

分离的直接收益：采集侧可以放心地执行「删源视频回收磁盘」「删重复文件」这类操作，
而不会危及已经花了上百小时转写出来的逐字稿。

## 2. 端到端数据流

```
① 采集          ② 音频              ③ 转写               ④ 归档
────────      ────────           ────────            ────────
账号/合集  ──►  .mp4     ──►  .m4a        ──►  逐字稿 md    ──►  夸克网盘
                │              ▲                 ▲
                └── 抽流 ───────┘                 │
                      或                         │
                 音频直下（跳过 mp4）──────────────┘

旁路：元数据 CSV（贯穿全程，是「存在性」判断的权威来源）
     封面图（采集时同步下载，最终与 md 同名存放）
```

关键点：

- **音频是分叉点**。可以走「先下 mp4 再抽流」，也可以「音频直下」完全跳过视频。
  两条路殊途同归，产物都是 `.m4a`，下游转写无感知。
- **CSV 是权威**。文件系统状态只是 CSV 的投影；两者的差异由自愈脚本负责收敛。
- **封面跟着作品走**。封面在采集阶段就下载（成本极低），转写阶段与 md 同名复制一份。

## 4. 端到端时序（每日一轮）

```
18:00  磁盘预检（不足则先回收，仍不足则整轮跳过）
18:01  _repair.py --apply            修数据：把「有记录但文件缺失」的作品放行重下
18:02  _pipeline.py                  账号增量采集（N 个账号串行；phase1 试水 + phase2 全量）
   ⋯    _dl_mix.py                   合集增量采集（单文件可达 1GB+，耗时较长）
   ⋯    _to_audio.py --delete        mp4 → m4a，删源视频回收磁盘
   ⋯    _seed_done.py --apply        已落盘作品回填下载 DB（防次日重下）
   ⋯    _cover_audit_fix.py          封面审计 + 三级兜底补齐
   ⋯    终检：_repair 缺失=0 且 _seed_done 待回填=0 → 汇报
~19:05 结束

20:00  _upload_alist.py --apply      增量上传新增 m4a + 封面到夸克网盘
   ⋯    小文件 ~2.5s/个；大文件 ~6MB/s；--jobs 3 ≈ 67 文件/分（脚本天然续传）
```

## 5. 设计取舍

### 5.1 为什么先抽音频再转写

- ASR 只需要声音，视频画面在转写场景完全无用。
- 实测：4 小时播客，视频 668 MB → 音频 81.8 MB（**省 88%**）。
- 抽流用 `-c:a copy`（无损、秒级），仅在容器不支持时才重编码 64k 单声道。

### 5.2 为什么要「音频直下」

正常流程是「下视频 → 抽音轨 → 删视频」，白下载了 8 倍的画面数据。
抖音的 Detail 接口其实直接提供纯音频档（DASH，`media-audio-und-mp4a`），
直接拉它就完全跳过了视频这一环 —— 尤其对 1GB+ 的长播客收益巨大。

### 5.3 为什么长视频必须切片转写

把一条 5 小时的音频整条丢给 ASR 服务，一旦中途崩溃就整条白跑（几十分钟到几小时）。
切成 15 分钟左右的段，每段独立落盘 + 独立登记，
崩了只重跑未完成的段，且已完成段永久复用。

### 5.4 为什么用 SQLite 而不是 JSON 记录状态

上传器/下载器都需要「已处理集合」；JSON 全量重写在长跑/并发下会丢更新。
上传状态库用 SQLite（`files` 表 + `runs` 表），并发写安全，且能直接查统计。

### 5.5 为什么终检要查「双 0」

单一检查会漏。`_repair` 查的是「有记录无文件」（会导致漏下），
`_seed_done` 查的是「有文件无记录」（会导致重复下载视频）。
两个方向都归零，才说明 DB 与磁盘真正一致。

## 6. 扩展一个新账号

1. 拿到账号主页分享链接（App 分享 → 复制链接），或直接 sec_uid（`MS4wLjAB...`）。
2. 入库（只拉清单 + 封面，不下视频）：
   ```bash
   python _acct_fetch.py <主页URL> --apply --covers
   ```
3. 把主页 URL 加进 `_pipeline.py` 的 `URLS` 列表（或 `settings.json` 的 `accounts_urls`）。
4. 补音频：`python _audio_direct.py --apply --fallback-video`（已有音频档直下，无则回退最小 mp4）。
5. 让转写侧识别：`lib_source.build_lib_tasks()` 会自动扫描 `UID*` / `MID*` 目录，无需改代码。
6. 跑一次全量体检：`_rename.py --apply`、`_repair.py`、`_seed_done.py --apply`、`_cover_audit_fix.py --check`。

> ⚠️ 纯数字的「抖音号」**不能**直接当 sec_uid 用，必须提供主页分享链接。
> 详见 [02-下载视频](02-下载视频.md#4-sec_uid-解析)。
