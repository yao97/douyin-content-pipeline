# 09 · 踩坑与排障索引

按「症状 → 根因 → 修法」组织。**每条都是真实踩过的**，附带所在脚本。

---

## A. 采集 / 下载

### A1. 只抓到每账号第一页（72 条）

- **症状**：第 1 页正常 18 条；第 2 页起响应头 `whale-decision-custom: black_no_login`，
  body 仅 17 字节 `{"status_code":0}`；日志报「配置文件 cookie 参数未登录，数据获取已提前结束」。
- **根因**：`src/testers/Params` 读的是 `Volume/test_cookie.ini`（与 `settings.json` 的正式 Cookie
  不是同一份，常已过期），且**从不注入 `uifid`/`msToken`**。
- **修法**：`await _tk_auth.inject(params)`；同时 `params.max_pages = 99999`。

### A2. 首轮全量提前终止

- **根因**：`accounts_urls[].earliest` 非空会触发 early_stop。
- **修法**：**首次全量必须留空**。

### A3. 合集模式污染次日任务

- **症状**：某天任务误跑成「下载合集」而不是账号增量。
- **根因**：`_dl_mix.py` 临时把 `run_command` 改成 `"5 5 1 Q"`，被强杀（timeout/SIGKILL）后没恢复。
- **修法**：`_pipeline.py` **每次运行都强制把 `run_command` 拉回 `"5 1 1 Q"`**。

### A4. 菜单索引 6 会永久卡死

- **根因**：`run_command` 的第 2 段索引 `6` = **后台监听模式（剪贴板监听）**。
- **修法**：只用 `"5 1 1 Q"`（账号）/ `"5 5 1 Q"`（合集）。官方文档里的示例已过时。

### A5. 下载进程崩在 safe-delete 守卫

- **症状**：工具批量清理 Cache 触发 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` →
  `main.py exit=1` → **后续账号静默不处理**（表现为「某账号永远差一部分」）。
- **修法**：所有子进程注入 `CODEBUDDY_SAFE_DELETE_ENABLED=0`
  （`_pipeline.py: run_helper()`、`_dl_mix.py`、`_run_cap.py` 均已内置）。

### A6. 磁盘写满导致整批中断

- **症状**：`OSError(28) 'No space left on device'`，DB 与落盘不一致。
- **修法**：`_pipeline.py: ensure_space()` 磁盘闸门 —— 不足时先 `_to_audio.py --delete` 回收，
  仍不足则**不启动下载**并 `exit=2`。

### A7. 纯数字抖音号解析不出 sec_uid

- **已试过且走不通**：SSR 页面 -404、`iesdouyin` 接口「参数不合法」、搜索页验证码、页面 fetch 缺签名。
- **修法**：**请用户提供主页分享链接**（App → 分享 → 复制链接）。
  可在「ppt 环境」的 Python（`playwright` 可用）里用有头模式解析 `v.douyin.com` 短链兜底：
  跟 302 → `iesdouyin.com/share/user/MS4wLjAB…`。

### A8. 下载「假成功」

- **症状**：某账号 0 下载但工具报成功（接口被间歇性拦截）。
- **修法**：跑完**必须**用 `_repair.py` 的缺失计数校验，缺了就重跑。

## B. 音频

### B1. 合集目录的 mp4 永不转音频

- **根因**：`_to_audio.py` 的 glob 只写了 `UID*_发布作品`，漏了 `MID*`（约 22 GB 白占盘）。
- **修法**：`glob("UID*_发布作品") | glob("MID*")`。

### B2. 音频直下误判「没有音频档」

- **症状**：并发探测报告大量作品「无音频档」，且**越早的作品越差**。
- **根因**：抖音限流时返回**降级响应**（content-length 约 60 KB vs 正常 125 KB+），
  `bit_rate` / `bit_rate_audio` 被整段裁掉。
- **修法**：`picked` 为空时 `sleep(2.5)` 退避后**重取一次详情**再判定。
  **绝不能用并发探测的「无音频档」结论。**

### B3. 兜底抽音轨抽出空文件

- **根因**：用了 `dash` 档 —— 它是**纯视频流，没有音轨**。
- **修法**：兜底只能选 `format == "mp4"`（渐进式、音视频混流）。

### B4. 半成品 m4a 被当成已完成

- **修法**：先写 `*. __tmp.m4a`，校验体积后再 `replace()`；
  已转换判据 `size > 1024`。

## C. 转写

### C1. 长视频整条提交一崩全废

- **修法**：`WB_SLICE_MIN`=1200s 自动切片；段长 `ceil(dur / ceil(dur/900))`。
  **必须向上取整 + 按浮点算**，否则会有碎屑尾段或覆盖不足。

### C2. 多源作品只转了第一片

- **根因**：`_stage1_run` 只取 `t["video"]`，`dur_est` 只算第一条源。
- **修法**：`srcs = slice_tasks(vid)`；`len(srcs) > 1` **一律强制切片**；`dur_est = sum(各源时长)`。

### C3. 「转写卡住了」

- **第一步永远先分清「真挂」和「只是看起来卡」。**
- 三层证据：① `stage1`/`stage2` 的 lock pid 是否存活 + 8766/8770 是否 200；
  ② **在飞作业有没有在吐字**（`/api/status/<job>` 的 `current_chunk` 在变长）；
  ③ 看板显示 `item.vid` 是否等于 `_slice_tmp/` 下**最新被写入**的目录名。
- 详见 [04-文案转写](04-文案转写.md#32-判卡住vs真在跑)。

### C4. 僵尸作业占住看板

- **症状**：看板显示「已跑 107:42 / 音频就绪 91.5% / 引擎无任何输出」。
- **根因**：8766 崩溃重启把内存里的 job 留给 DB 恢复成 `audio_ready` 且永不推进；
  看板若「优先找活跃的」就会被它盖住。
- **修法**：作业按 `created_at` 倒序取第 0 个（**最新提交的才是当前有效的**）；
  看板条目打分取最大 + 僵尸过滤器（`LIVE_JOB_WIN`）。

### C5. `load_registry()` 读失败必须抛错

- 旧实现静默返回 `{}` ⇒ 被判「所有作品都没转过」⇒ 全量重转（上百小时、不可逆）。
- 现在：重试一次 → 备份 `.corrupt` → 抛 `RuntimeError`。**这是有意设计，不要去"修"**。

### C6. 注册表改动被静默抹掉

- **症状**：`accept` 不生效、条目被重转、`retry` 放行后仍 `abandoned`。
- **根因**：整表回写（长跑进程会覆盖别人的改动）。
- **修法**：读走 `_reg()`（按 `(mtime_ns, size)` 指纹自动重载），
  写一律 `update_entry(vid, patch, remove, delete)`。

### C7. 数崩溃数不准

- **根因**：`service.err.log` 会轮转（历史在 `service.err-<时间戳>.log`）；
  工作区 `_asr_server.log` 在 nssm 托管时**根本不更新**（mtime 可能是几小时前）。
- **修法**：两个文件都看；用 Python 逐行扫、缓存最近一条时间戳再命中 `GGML_ASSERT`。

### C8. 手工 `slice` 与 stage1 撞车

- **根因**：`slice` 子命令**不取 `_stage1.lock`** ⇒ 同一段音频产生两个 job（服务端单 worker 串行，耗时翻倍）。
- **修法**：要手工补跑，先确认 stage1 已收工；否则直接拉 stage1 让它自己跑。
  **服务端没有 cancel 接口，只能提前防。**

### C9. 看板看起来卡死

- **`stream_src=log` 是陷阱**：取不到 `current_chunk` 时回退读工作区 `_asr_server.log`
  （nssm 托管时不更新）→ 显示几小时前的陈旧文本。正常应是 `stream_src=engine`。

### C10. ⚠️ 铁律：不要杀进程

- 实测误杀正在跑的 stage1 → 跑批白停 1 小时，服务端其实已完成、只是没人取结果，整段作废。
- **单实例锁（O_EXCL）已能防重复；陈旧锁会在下次拉起时自动接管 —— 不需要任何人工清理。**
- 重启看板用 `POST /api/quit`，**不要 `taskkill`**。

### C11. 双层进程不是重复实例

- 本项目每个长跑脚本在 `tasklist` 里都呈现**（小 RSS 父进程, 大 RSS 子进程）同命令行**成对出现
  （Windows venv 启动器特性）。父进程 ppid 指向 nssm 或启动器。
- 判重看：`lock` 里的 pid 是否存活 + **同一命令行只应有 1 组**。

## D. 命名 / 封面 / 数据一致性

### D1. 合集被误判「全部缺失」

- **根因**：`MID_` 目录不参与 `_rename.py`，文件名仍是工具原始命名（**没有作品ID**）。
- **后果**：`_repair.py --apply` 会删掉全部合集 DB 记录 → **下次重下几十 GB**；
  `_cover_audit_fix.py` 每轮误报缺封面。
- **修法**：**双前缀匹配**（标准名 + 原始命名）。
  **新增校验脚本请复用 `_mix_verify.py` 的口径。**

### D2. 图集被判「缺封面」并重复下载

- **修法**：只有 `_N` 图时，**用首图复制一份**成标准名 `{date}_{nick}_{id}.{ext}`。

### D3. 幽灵记录导致视频永久漏下

- **根因**：封面与视频共用同一 `aweme_id` 写记录 ⇒「封面成功 + 视频失败」被标为已下载。
- **修法**：`_repair.py --apply`（删记录 + 清孤儿缓存）。**每次下载前先跑。**

### D4. 已有 m4a 的作品被重复下载视频

- **根因**：工具 `is_exists()` 查的是它自己的命名路径，与库里的标准名对不上。
- **修法**：`_seed_done.py --apply` 把 ID 写回 `download_data`。
  **与 `_repair.py` 成对使用。**

### D5. CSV 重复行

- **根因**：多次采集会重复追加同一作品。
- **修法**：读 CSV 建映射时一律 `set()` 去重（`_rename.py` 已处理）。

### D6. CSV 列结构变更

- 早期 6 字段版本已被 30 列版本覆盖。
- **修法**：读 CSV **一律按列名取值，不要按位置索引**。

## E. 云端归档

### E1. 上传后回查「失败」（其实成功）

- **根因**：alist 目录列表有缓存（`cache_expiration` 曾为 30 分钟）。
- **修法**：**不要逐文件 `fs/get`**；改为按目录 `list_dir(refresh=True)` 批量比对 size；
  并把目标存储的 `cache_expiration` 设为 `0`。

### E2. 自签 JWT 一律 `token is invalidated`

- **根因**：`Auth()` 除 claim 外还校验设备会话 `md5(userID + Client-Id)` 与 `PwdTS`。
- **修法**：改用**全局 API 令牌**（`x_setting_items(key='token')`）。**不要再爆破。**

### E3. 夸克建目录/上传 401

- **根因**：夸克读接口 Cookie 能通，**写接口需要签名**。
- **修法**：写操作一律经 alist 驱动。

### E4. 上传到半成品 / 云端孤儿

- **根因**：与采集链并行（采集链会重下封面 + `_rename.py` 删重复，文件在动）。
- **修法**：`--min-age-min`（默认 15）冷却 + 把上传链排在采集链结束之后。

### E5. alist 存储配置写入报 `ReadBool: expect t or f`

- **根因**：SQLite 里是 `0/1`，而 Go 结构体的 bool 字段要求真正的布尔字面量。
- **修法**：更新存储配置时布尔字段发 Python `True/False`，不要发 `0/1`。

### E6. `near "order": syntax error`

- **根因**：`order` 是 SQL 保留字。
- **修法**：SELECT 时加引号，或改用 `/api/admin/storage/list`。

## F. 本机环境

### F1. 中文输出双重乱码

- **根因**：PowerShell `*>` 会按 GBK 二次编码。
- **修法**：用 `_run_cap.py`（`python _run_cap.py <out.txt> <cwd> <exe> [args...]`），
  自动注入环境变量 + 自动 utf-8→gbk 解码后写文件。
  **跑 `_to_audio` / `_cover_audit_fix` / `_repair` / `_pipeline` 一律套它。**

### F2. PowerShell 工具 stdout 不回显

- **修法**：结果 `Out-File` / `Set-Content` 落盘，再用 Read 读。

### F3. `unlink()` / `Remove-Item` 被 safe-delete 拦截

- **现象**：删除操作被走回收站，且回收站操作可能失败报 `SAFE_DELETE_FAIL_CLOSED`。
- **修法**：只有 `[System.IO.File]::Delete()`（PowerShell）或
  Win32 `DeleteFileW`（Python `ctypes`）能直接删除。
  脚本里见 `_rename.py: hard_delete()` / `_audio_direct.py: hard_delete()`。

### F4. 系统代理劫走本地请求

- **根因**：本机有 Clash 监听 `127.0.0.1:7890`。
- **修法**：本地请求必须 `trust_env=False`（requests）/ `--noproxy '*'`（curl）/
  `build_opener(ProxyHandler({}))`（urllib）。

### F5. 杀进程必须按命令行过滤

- 必须按 `CommandLine` 过滤 `*TikTokDownloader*`，**绝不可误杀**：
  `transcribe_server.py --port 8766`（共享 ASR 服务，常驻）、
  `fun-asr/asr_server.py`、`video-analyzer` 的 `asr_batch.py` / `_stage2_daemon.py`。

### F6. 双网卡出口漂移

- WLAN `192.168.0.8`（**局域网服务对外地址**）、有线 `192.168.0.9`，同网关。
- 自动跃点会随链路速率漂移 → 排查先 `Find-NetRoute -RemoteIPAddress 223.5.5.5` 确认出口。
- **不要轻易重启网卡**：会重新 DHCP，IP 变动会导致外部设备按 `.0.8` 访问失败。
