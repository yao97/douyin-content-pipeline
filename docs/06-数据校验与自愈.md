# 06 · 数据校验与自愈

「DB 记录」与「磁盘文件」会漂移。本环节用两个互补的脚本把两个方向都收敛到 0。

---

## 1. 漂移是怎么产生的

工具（TikTokDownloader）的跳过判断是：

```python
is_skip(id) = is_downloaded(id) or is_exists(工具目标路径)
```

其中 `is_downloaded` 查 DB 的 `download_data(ID)`。

### 1.1 幽灵记录（有记录 · 无文件）→ 漏下

工具源码里，**封面和视频共用同一个 `aweme_id` 写记录**：
`download_file()` 每下成功「任意一个」文件就 `update_id()`。

于是：

```
封面下载成功  →  记录 ✓
视频下载失败/中断  →  记录仍然 ✓
─────────────────────────────
结果：作品被标记「已下载」，下次 is_skip 命中，视频永久漏下
```

同时 `Volume/Cache/` 里会留下**孤儿半成品**（下到一半的分片），
若不清掉，续传时可能拼接出损坏文件。

### 1.2 有文件 · 无记录 → 重复下载

反向情况：本地已经有 `.m4a`（音频直下补的），但 DB 里没有这条 ID。

工具的 `is_exists()` 检查的是**工具自己的命名路径**
（`{create_time}-视频-{昵称}-{描述}.mp4`），而库里的文件叫 `{日期}_{昵称}_{ID}.m4a` —— 两条都不命中，
于是被当成「没下过」，**次日重新下载整个视频**。

## 2. 修幽灵记录（`_repair.py`）

**以 `Data/*.csv` 为准**（CSV 含「作品ID + 发布时间」，标准文件名以发布时间开头），
找出「库里有记录但对应文件不存在」的作品：

1. 删 `download_data` 里这些 ID（下次运行会重新下载）；
2. 删 `Volume/Cache` 里这些作品的孤儿半成品。

```bash
python _repair.py           # 只报告（dry-run）
python _repair.py --apply   # 真正执行
```

> ⚠️ **必须在工具进程未运行时执行**（避免 SQLite 锁冲突）。

### 2.1 两个关键设计

**(a) 双前缀匹配**（见 [05-命名与封面](05-命名与封面.md#2-️-命名一致性陷阱踩过两次代价很大)）：
同时接受 `{日期}_{昵称}_{ID}` 与 `{发布时间冒号换点}-`，
否则会把整个合集目录误判为缺失，`--apply` 会删掉全部合集记录 → 重下几十 GB。

**(b) 永久跳过名单**：

```python
PERMANENT_SKIP = {x["id"] for x in json.loads((ROOT / "_skip_ids.json").read_text())["ids"]}
stale = (set(missing) & recorded) - PERMANENT_SKIP
```

`_skip_ids.json` 里是**源端已损坏、永远下不到**的作品（例如源音频 AAC 损坏、
或作者已删）。这些作品的记录**不可删** —— 删了也无济于事，只会让每轮都重试一遍。

> 配套脚本 `_mark_skip.py`：把名单里的 ID **写回 DB**，防止重复下载。

**判「落盘」的扩展名口径**：

```python
VIDEO_EXT = ("*.mp4", "*.m4a")            # 有音轨也算落盘
IMAGE_EXT = ("*.jpeg", "*.jpg", "*.webp", "*.png")
# 图集/实况看图片；视频类看 mp4/m4a
```

这与下面的 `_seed_done.py` **必须相容**，否则会互相拆台。

---

## 3. 回填下载记录（`_seed_done.py`）

把「已落盘的作品」ID **写回 DB**，使增量任务跳过，不再重复下载视频。

```bash
python _seed_done.py                       # dry-run：只统计
python _seed_done.py --apply               # 写入
python _seed_done.py --apply --folder UID..._魏远麟律师 广州_发布作品
```

```python
con.executemany("INSERT OR REPLACE INTO download_data (ID) VALUES (?)", [(w,) for w in need])
```

**与 `_repair.py` 成对使用**：

| 脚本 | 方向 | 动作 |
|---|---|---|
| `_repair.py` | 有记录 · 无文件 | 删记录（放行重下） |
| `_seed_done.py` | 有文件 · 无记录 | 补记录（防止重下） |

`_repair.py` 判「落盘」时接受 `.m4a`，所以不会把 `_seed_done` 刚补的记录当幽灵删掉 ——
**这个相容性是被刻意维护的**。改动任一方都要同步复核另一方。

## 4. 合集核验（`_mix_verify.py`）

合集目录专用的核验脚本，演示了正确的**原始命名前缀口径**：

```python
def prefix(ts: str) -> str:
    d, _, t = ts.partition(" ")
    return f"{d} {t.replace(':', '.')}"

missing = [wid for wid, (ts, desc) in records.items()
           if not any(n.startswith(prefix(ts)) for n in names)]
```

- 默认只报告；
- `--apply` 时删除这些缺失 ID 在 DB 里的幻影记录。

## 5. 终检：「双 0」口径

单一检查会漏，所以每日链路的终检要求**两个方向同时归零**：

```
_repair.py     → 缺失计数 = 0      （没有「有记录无文件」）
_seed_done.py  → 待回填计数 = 0    （没有「有文件无记录」）
────────────────────────────────────────────
两者皆为 0  ⇒  DB 与磁盘真正一致
```

再叠加两项抽查：

```
_rename.py --apply            → 「匹配 0 个」（没有待改名文件残留）
_cover_audit_fix.py --check   → 「缺封面 0」
```

四项全 0 才算这一轮采集干净收尾。

---

## 6. ⚠️ 假成功

接口被间歇性拦截时，工具会「**0 下载但报成功**」。所以**跑完必须校验缺失计数**，
缺了就重跑该账号。这也是终检存在的直接原因。
