# 11 · 跨机转写（外机与生产机**不在同一网络**）

> 场景：转写是整条链最重的一环（112h 音频在本机要跑好几天，且 ASR 引擎会因 KV 溢出
> 周期性硬崩）。把**转写算力**搬到另一台带独显的 Windows 机器，产出回传，本机只做裁决与渲染。

## 1. 为什么是「只交 raw」，不是「交 md」

`_asr_registry.json` 是增量重跑的**唯一真相**，必须遵守**单一写者**原则 ——
两台机器同时跑跑批会互相覆盖（历史坑：长跑进程用旧缓存「整表回写」，
把别处刚写的改动**静默抹掉**，症状是 `accept`/`retry` 不生效、条目被重转）。
所以：

| 角色 | 写什么 | 不写什么 |
|---|---|---|
| 外机 | `_asr_raw/<vid>.json`（转写原文） | ❌ 不写 `_asr_registry.json`、❌ 不出 md |
| 本机 | 注册表（逐条 `update_entry`）+ md（`stage2`） | — |

> 本机的注册表写入 2026-10-01 起还多了一层 **跨进程字节锁**（`_reg_guard()`）：
> `stage1` / `checkpoint.py`（detached，会真并行）/ 人工 CLI / `fetch --apply`
> 四个写者同时改不同 vid 时，原来会在毫秒级窗口**丢更新**（实测无锁丢 82%）。
> 详见 §6。**但「外机不写注册表」这条原则不变** —— 锁只解决本机进程间竞争。

好处：① 天然无跨机冲突 ② 关键词 / LLM 摘要 / 封面 / 命名规范 100% 与本机一致
③ raw 极小（平均 **34 KB/条**），回传成本可忽略。

### 体积账（真实口径）

| 走法 | 单向流量 |
|---|---|
| 外机整链跑、只回 raw | 源 **3.68 GB 已在夸克**（本机零上传）＋ 回传 raw **~11 MB**/327 条 |
| 改「把音频推给远端 8766 算」 | **12.03 GB**（112.1h ÷ 879s ≈ 459 段 × ~27MB） |

→ 差 **400 倍**。**不同网络下只有前者成立**（后者还需把 8766 暴露到公网，
而 8766 的 `/api/*` 零鉴权 —— 绝对不要）。

## 3. 搬运通道（夸克网盘）

两端约定一个固定的**交接目录**，都在夸克里：

```
自媒体视频库/_跨机交接/
├── to_remote/     ← 本机放清单（3 个文件，~330 KB）
└── from_remote/   ← 外机放回传包（1 个 zip，~11 MB）
```

### 3.1 通道选择（**踩过的坑，别走错**）

| 通道 | 列目录 | 上传 | 下载 |
|---|---|---|---|
| **alist**（Quark 驱动） | ✅ | ✅（采集流水线每天在用） | ❌ **直链被夸克 CDN 拒**：`RequestDeniedByCallback` / `require login` |
| **夸克官方 CLI**（开放平台令牌） | ⚠️ **受限视图** | ✅ 但只在它自己的沙箱根下 | ✅ 但够不到 `自媒体视频库` |
| **夸克 web API + 会话 cookie** | ✅ | 需签名，不做 | ✅ **可用**（本工具走这条） |

结论：**列目录/上传走 alist，下载走夸克 web API**。

- 夸克官方 CLI 的令牌是**受限视图**（`browse --parent-fid 0` 只看到 2 个目录；
  直接按源库 fid 取会返回 `12005 文件无权限`），所以它做不了这条链的搬运。
- alist 的下载直链指向 `dl-pc-zb.pds.quark.cn`，实测 403 ——
  这是 **alist 侧的既有问题**（不影响它的上传与列目录）。
- 夸克 web 通道的 cookie 直接复用 alist 存储配置里的那份
  （`/api/admin/storage/list` → `addition.cookie`），不需要额外登录；
  `fs/get` 返回的 `id` 就是夸克的文件 FID，拿它调 `file/download` 换一次性直链。

### 3.2 ⚠️ 目录名对不上（最容易踩）

| | 目录名 |
|---|---|
| 夸克网盘（`自媒体视频库/` 下） | `魏远麟律师 广州` |
| 本机库（= 清单 `src_rel` 的第一段） | `UID3303366684053592_魏远麟律师 广州_发布作品` |

映射规则以采集侧上传器 `_upload_alist.account_of()` 为**权威**（`remote_handoff` 直接调它，
避免两处规则漂移）。所以清单里给**两套路径**：

- `src_quark` —— **从哪取**（夸克上相对 `自媒体视频库/` 的位置）
- `src_rel` —— **放到哪**（外机本地相对 `WB_LIB_ROOT` 的位置）

### 3.3 外机「直接传 alist」，本机收得到吗？

**收得到 —— 但不是直连本机的 alist**，这点必须先掰清楚：

| 问 | 答 |
|---|---|
| 外机能直接 `PUT` 到本机 `alist` 吗？ | ❌ 不能。本机 alist 监听 `0.0.0.0:5244`，**只有局域网可达**（同 `8766`/`8770`）；外机不在同一网络，`192.168.0.8:5244` 探测直接超时 |
| 那外机要怎么做才算「直传」？ | ✅ 把文件放进**同一个夸克账号**的 `自媒体视频库/_跨机交接/from_remote/`。外机若也装了 alist 且指向**同一个夸克账号**，用 alist 上传即可；懒一点就用夸克客户端网页/客户端手动上传 —— 两条路等价 |
| 本机怎么收到？ | `python remote_handoff.py fetch --apply`（alist 列目录 → 夸克 web 通道下载） |

依据：alist 的 Quark 存储 `root_folder_id` 指向的就是那个账号的那份目录，
所以**本机 alist 与夸克后台读的是同一份数据**（实测两个 Quark 存储同属账号 `夸父3929`）。
已做最小往返验证（等效模拟外机经 alist 上传）：

```
① 本机 alist put_file → /自媒体视频库/_跨机交接/from_remote/probe.zip   → ok 227B
② 本机 alist list_dir(refresh=True) 立刻可见 probe.zip
③ 绕开 alist、用夸克 web API 独立取回 → 227 字节，内容完全一致
```

两个附带结论：

- **下载直链两端都不通**：alist `fs/get` 给的 `raw_url` 指向夸克 CDN，实测 403；
  `/d/<path>?sign=` 会 302 到 `RequestDeniedByCallback`。
  → 所以「先传、后用」，本机靠夸克 web 的 `file/download`（`fid` 取自 alist `fs/get` 的 `data.id`）。
  **这是既有问题，与跨机改动无关**（采集流水线只用上传，所以一直没暴露）。
- **想挂守候式自动收包**（每 N 分钟自动 `fetch`）技术上可行，但**前提是注册表写锁已生效**
  —— 见 §6。

## 4. 三步流程

### ① 本机导出 + 发布清单

```bash
cd <本机知识库目录>
python remote_handoff.py export          # 出清单（to_remote.json + 两份 md）
python remote_handoff.py publish         # 推到夸克 自媒体视频库/_跨机交接/to_remote/
python remote_handoff.py publish --check # 只比对远端现状，不上传
```

`export` 支持 `--author 魏远麟` / `--limit 50` 分批。清单里每条给出
`src_rel` / `src_quark` / `cover_rel` / `cover_quark` 与 `size` / `dur_sec`。
`外机操作说明.md` 是**给外机看的完整操作手册**（含目录改名脚本）。

### ② 外机拉源 + 转写

外机只需下 4 个夸克目录（约 6 GB），改名成 `src_rel` 的目录名，设好环境变量后：

```bash
python asr_batch.py stage1
```

只产 `_asr_raw/<vid>.json`。长视频（≥20 分钟）**自动切片**并合并成一条，
每段独立落盘可断点续跑；引擎崩了客户端会自愈重提。

回传：把清单里那些 vid 的 json 打成一个 zip，传到
夸克 `自媒体视频库/_跨机交接/from_remote/`。（`外机操作说明.md` 里有现成的 PowerShell 片段。）

### ③ 本机一键收包 + 渲染

```bash
python remote_handoff.py fetch            # 先 dry-run：拉最新 zip + 预演
python remote_handoff.py fetch --apply    # 合入 + 逐条登记注册表
python _stage2_daemon.py                  # 渲染 raw → md（若已在跑会自动捡到）
```

`fetch` = **经 alist 列目录挑最新 zip → 走夸克 web 通道下载 → 自动解压 → 导入**。
也可以手动下载后 `python remote_handoff.py import <目录|zip> --apply`。

`import` 做四件事：**① 校验**（空 text / duration 无效 / 字数过短一律拒收）
**② 去重**（本机已转写的跳过）**③ 用本机源元数据覆盖** `author/pub/title/account/kind/aid/video/cover`
**④ 原子落盘**（`.part` → `os.replace`，stage2 轮询不会读到半截文件），最后**逐条 `update_entry()` 登记**。

> ⚠️ 这里**刻意不用 `build_registry()`**（2026-10-01 改）。它是「扫描全量 → 整表覆盖」，
> 在 `stage1` 正在跑的时候有两处真伤：
> ① 每条只写 7 个基础字段，会把 `abandoned` / `note` / `retry_rounds` 等**管理字段抹掉**
>   → 已判「放弃」的作品被当成没转过，跑批重转一遍（代价不可逆）；
> ② 整表覆盖发生在扫描快照**之后**，扫描窗口内 `stage1` 刚写的新条目会被旧快照盖掉。
> 需要全量重建时用 `asr_batch.py registry`，且**跑批停止时**才跑（它会先打印警告）。
> 隔离实测：同样造一条带 `abandoned/note/retry_rounds` 的条目，
> `build_registry()` 之后只剩 `['author','chars','duration','job_id','ok','pub','ts']`。

> 为什么非要 ③：raw 里的 `video` / `cover` 是**外机的绝对路径**，本机不存在 ——
> `cover` 不存在会让 md「生成了但没有同名封面」，`video` 不换则 raw 溯源失真。
> import 时按 vid 从本机库里重新解析出真实路径，顺带把外机可能填错的元数据一并纠正。
> 若本机确实找不到封面，会明确告警列出 vid（而不是静默出无封面 md）。

## 5. 分工与避坑

- **别两台同时转同一条**。要么按作者/`--limit` 切分，要么本机先停 `stage1`
  （`_stage1.lock` 的 pid 存活判定会让第二个实例自己退出，但**重复转写**是白烧时间）。
- 外机转完的条目，本机 `_todo()` 自然不再列出（注册表已 ok）→ 不会重复派发。
- **外机不写注册表、不出 md、不碰 `_slice_tmp` 回传**。
- 外机不需要 `Data/UID*.csv` / `facts.json`；文件名里已带作品ID与日期，
  作者取自目录名（改名后 `UID…_作者_发布作品` 就自洽了）。
- 外机下的目录里同名 `.webp` 封面是历史遗留，`.jpeg` 优先，两个都在也无妨。
- 若某条在外机反复失败：先按 `docs/09-踩坑与排障.md` 的「失败归因三步法」判，
  AAC 码流损坏类**只能重新下载**，换机器也没用。
- 回传包里塞了非 json / 非法路径的 zip 会被**拒绝解压**（防目录穿越），
  不合格条目逐条列出原因，不会污染本机 raw。

## 6. 注册表并发与写锁（`_reg_guard()`）

**为什么要有这层锁**：`update_entry()` 已经做到「先重读磁盘、只改自己那条」，
但它仍是 **load → modify → save 三步**。两个进程改**不同** vid 时，若两次 load 都发生在
对方 save 之前，后 save 的那份表就不含对方改动 → **静默丢更新**。
窗口 = 读写一次注册表（700+ 条）的时间，毫秒级 —— 单次跑批撞上概率低，
但**长期并行的四个写者**会被反复撞：

| 写者 | 会不会与 `stage1` 并行 |
|---|---|
| `stage1` 每条转完 `update_entry()` | — |
| `checkpoint.py` 定期 `retry_infra()` | ✅ **会**（`Popen` 是 detached，能活过 checkpoint 退出） |
| 人工 `accept` / `retry` / `registry` | ✅ 会 |
| `remote_handoff.py fetch --apply` | ✅ 会（守候式自动收包时必然） |

隔离压测（8 进程 × 40 次各写自己的 vid，共 320 条）：

| 版本 | 存活条目 | 丢率 |
|---|---|---|
| 无锁（加锁前） | 56 / 320 | **82.5%** |
| 加锁后 | 320 / 320 | **0** |

**实现（`asr_batch.py` 的 `_RegGuard` / `_reg_guard()`）**：

- 进程内 `threading.RLock`（同进程重入直接放行、多线程串行）；
- 跨进程用**内核字节锁**：Windows `msvcrt.locking(LK_NBLCK)` / POSIX `fcntl.flock(LOCK_EX|LOCK_NB)`；
- **降级**：拿不到锁就自旋，超 `WB_REG_LOCK_SEC`(20)s 放弃加锁直接执行 ——
  宁可保留极小概率丢更新，也不能让跑批卡死；
- 环境变量：`WB_REG_LOCK_SEC`(20) / `WB_REG_LOCK_POLL`(0.005)。

> ⚠️ **别退回「`O_EXCL` 建锁文件 + `os.remove` 释放」**（第一版就踩了）：
> Windows 上 `os.remove` 是**标记删除**（delete pending），窗口期别的进程 open 同一路径
> 直接 `PermissionError: Errno 13` —— 这不是「锁被占」却被当成异常抛出；且进程被 kill 时
> 锁文件残留，得靠 stale 超时（120s）兜底，跑批白等。
> 改成内核字节锁后：占用与否表现为「锁不上」而非抛异常，**进程被杀由 OS 自动释放**
> （实测强杀持有者后，另一进程 **0.00s** 立即拿到锁），锁文件因此**永不删除**、常驻无害。

**已套锁的写入路径**：`update_entry()`（含 `accept`/`retry`/`mark_ok` 等所有调用方）、
`retry_infra()`（整段「读全表→批量改→写回」入锁）、`build_registry()`（锁覆盖
**「扫描 → 写回」全程**，不只是 save）。

> **⚠️ 改代码后必须重启才生效**：`stage1` / `_stage2_daemon.py` 都是长跑进程，
> `import asr_batch` 只发生一次。正在跑的实例仍是旧模块（无锁）。
> 另外 `registry` 模式是**整表覆盖**，跑批进行中执行会打印警告 —— 等跑批结束再重建。
